# **Web UI 工程实施方案**

## **----将 Layer 0 + 14 Modules 封装成一个用户只需"上传 → 配音 → 下载"的影视 AI 配音平台**

这部分**不改变我们已经确定的 Layer 0 + 14 模块架构**。Web UI 是它们之上的**表现层与控制层**：
    
    
                             用户
                              │
                              ▼
                  ┌─────────────────────┐
                  │       Web UI        │
                  │                     │
                  │ ① 输入原视频        │
                  │ ② 配音任务          │
                  │ ③ 输出配音视频      │
                  └──────────┬──────────┘
                             │
                             ▼
                    ┌────────────────┐
                    │   UI Backend   │
                    │  API / WebSocket│
                    └────────┬───────┘
                             │
                             ▼
                    ┌────────────────┐
                    │    Layer 0     │
                    │ Workflow       │
                    │ Selector       │
                    │ Orchestrator   │
                    └────────┬───────┘
                             │
                 ┌───────────┼───────────┐
                 ▼           ▼           ▼
                M01         M02         M03
                 │           │           │
                 └───────────┼───────────┘
                             │
                           ...
                             │
                             ▼
                            M14
                             │
                             ▼
                     配音后最终视频
                             │
                             ▼
                          Web UI

**用户永远不需要知道 M01～M14 的存在。**

# **一、UI 的核心原则**

我们的平台不是"专业视频编辑软件"，而应该接近：

**把一部外语影视剧变成中文配音版。**

因此第一版 UI 必须极简。

用户进入页面后看到：
    
    
    ┌──────────────────────────────────────────────┐
    │              AI影视配音                      │
    │                                              │
    │  原始视频                                    │
    │  ┌────────────────────────────────────────┐  │
    │  │                                        │  │
    │  │       拖入视频文件                     │  │
    │  │       或点击选择视频                   │  │
    │  │                                        │  │
    │  └────────────────────────────────────────┘  │
    │                                              │
    │  配音语言： [ 中文 ▼ ]                       │
    │                                              │
    │  质量：     [ 标准 ▼ ]                       │
    │                                              │
    │              [ 开始配音 ]                    │
    │                                              │
    └──────────────────────────────────────────────┘

就够了。

# **五、最重要的设计：Web UI 绝对不能直接调用 14 个模块**

错误架构：
    
    
    Browser
     ├── M01 API
     ├── M02 API
     ├── M03 API
     ├── M04 API
     ...
     └── M14 API

这样 UI 很快会变成灾难。

正确架构：
    
    
    Browser
       │
       ▼
    Web API
       │
       ▼
    Layer 0
       │
       ▼
    Workflow
       │
       ▼
    M01 → M02 → ... → M14

Web UI 只认识：
    
    
    Project
    Job
    Input
    Output
    Status

# **二十二、状态机**

Web UI 必须使用 Layer 0 的状态，而不是自己猜。

例如：
    
    
    CREATED
       ↓
    QUEUED
       ↓
    ANALYZING
       ↓
    PROCESSING
       ↓
    PAUSED
       ↓
    PROCESSING
       ↓
    COMPLETED

异常：
    
    
    PROCESSING
        ↓
    FAILED
        ↓
    RETRYING
        ↓
    PROCESSING

人工：
    
    
    WAITING_HUMAN

# **二十三、一个非常重要的原则**

## **Web UI 永远不能修改 Module 内部状态。**

例如用户点击：
    
    
    暂停

不是：
    
    
    M07.stop()

而是：
    
    
    POST /jobs/{id}/pause

然后：
    
    
    Web API
     ↓
    Layer 0
     ↓
    Scheduler
     ↓
    当前 Module

这样 Layer 0 永远是唯一的任务状态权威。

* * *

# **二十四、视频上传也不要直接交给 Module**

流程：
    
    
    Browser
     ↓
    Upload API
     ↓
    Media Intake
     ↓
    Artifact Registry
     ↓
    Layer 0

上传完成以后才创建 Job。

这样大文件上传失败不会影响任务调度。

* * *

# **二十五、支持断点续传**

影视文件可能几个 GB。

所以：
    
    
    上传

应该支持：
    
    
    chunk upload

例如：
    
    
    video.mp4
     ↓
    chunk 001
    chunk 002
    ...
    chunk 500

上传中断：
    
    
    继续上传

而不是重新上传。

* * *

    grill-with-docs

           ↓
    to-tickets
           ↓

           ↓
    implement
           ↓
    tests
           ↓

# **三十四、最终整个工程变成三层**

这是我建议最终冻结的总架构：
    
    
    ┌─────────────────────────────────────────────┐
    │                 用户层                      │
    │                                             │
    │             React Web UI                   │
    │                                             │
    │     输入视频 → 配音任务 → 输出视频          │
    └──────────────────────┬──────────────────────┘
                           │
                           ▼
    ┌─────────────────────────────────────────────┐
    │                 控制层                      │
    │                                             │
    │                 Layer 0                     │
    │                                             │
    │ Workflow Selector                           │
    │ Planner / Scheduler                         │
    │ State / Checkpoint                          │
    │ Dependency / Recovery                       │
    │ Resource / Quota                            │
    └──────────────────────┬──────────────────────┘
                           │
                           ▼
    ┌─────────────────────────────────────────────┐
    │                 执行层                      │
    │                                             │
    │ M01 → M02 → M03 → ... → M14                │
    │                                             │
    │ 每个模块独立、串行、可替换、可恢复           │
    └─────────────────────────────────────────────┘

而**Pi + GLM-4.7 在这三层之外**：
    
    
                        Pi + GLM-4.7
                             │
                      软件工程施工工具
                             │
                             ▼
                  创建/测试/维护上述系统

这样整个架构就彻底清晰了：

**Pi 负责"把平台造出来"；Web UI 负责"让父母可以简单地使用平台"；Layer 0 负责"把14个模块组织起来"；14个模块负责"真正完成配音"。**

这也是我认为目前最适合我们这个项目的最终分层。
